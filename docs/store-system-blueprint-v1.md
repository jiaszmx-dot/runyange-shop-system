# 门店经营系统作战蓝图 V1

## 1. 项目目标

在 90 天内交付一套可部署、可在门店真实使用、支持多店模型的门店经营系统 1.0，服务样本店并为直营连锁与加盟管理预留扩展能力。

## 2. 核心战略结论

### 2.1 第一版必须是“可用的业务系统”，不是“完美的平台”

- 所有核心闭环都要覆盖
- 但每个模块第一版深度要受控
- 先打通“会员 -> 开单 -> 服务 -> 扣费/支付 -> 提成 -> 库存 -> 报表 -> 回访”

### 2.2 第一版以“PC 后台 + 手机网页”作为主交付形态

- 原因：
  - 开发成本最低
  - 最适合单人快速交付
  - 收银、表格、报表、多店配置在 PC 上效率更高
  - 手机网页足够覆盖收银员和员工的高频操作
- 小程序不取消，但建议放到第二阶段

### 2.3 真实支付不能卡住首发上线

- 先按“支付抽象层”设计
- 第一版可先支持记账型支付
- 同时并行准备微信/支付宝商户接入
- 资质、审核、联调准备好后再切真实支付

### 2.4 多店不是附加功能，而是底层架构前提

- 从第一天开始按多租户模型设计
- 总部、直营店、加盟店权限模型必须先定

## 3. 第一版产品边界

### 3.1 必须交付模块

1. 组织与多店管理
2. 账号、角色、权限
3. 会员与家庭档案
4. 充值方案与赠送规则
5. 服务项目与商品管理
6. 收银开单
7. 储值、次卡、赠送次数扣减
8. 多项目、多员工提成
9. 商品库存与关键耗材扣减
10. 退款、撤单、充值退款、提成反结算
11. 活动券与二维码核销
12. 回访记录与自动提醒任务
13. 基础经营报表
14. 小票打印基础方案
15. 审计日志

### 3.2 第一版暂不深做的模块

1. 预约与排班
2. 高级营销自动化编排
3. 复杂加盟结算和分账
4. 深度 BI 可视化
5. 小程序原生版
6. 复杂审批流

## 4. 关键业务模型

### 4.1 多组织模型

- 平台
- 品牌总部
- 门店
- 门店类型
  - 直营
  - 加盟

### 4.2 权限模型

- 总部超级管理员
- 总部运营
- 店长
- 收银员
- 员工/技师

### 4.3 数据权限原则

- 总部可查看所有门店经营数据
- 总部可直接编辑直营店业务数据
- 总部对加盟店默认只有查看权和规则下发权
- 加盟店自行处理本店收银、充值、退款、员工和会员数据
- 项目、价格、活动使用“总部模板 + 加盟店授权覆盖”模型

### 4.4 会员模型

- 会员主档案
- 家庭档案
- 孩子/家庭成员档案
- 储值余额账户
- 次卡/疗程包账户
- 赠送次数账户
- 消费记录
- 回访记录
- 标签与备注

### 4.5 订单模型

- 一张订单支持：
  - 多服务项目
  - 多商品
  - 多员工
  - 不同支付方式组合
  - 使用余额、次卡、赠送次数混合结算

### 4.6 提成模型

- 服务提成：按项目固定额或固定规则
- 充值提成：按充值方案阶梯比例
- 退款后自动反结算
- 提成需保留快照，避免后续规则变化影响历史账

## 5. 技术路线建议

## 5.1 技术栈

- 前后端形态：单体全栈 Web 应用
- 语言：TypeScript
- 前端：Next.js
- 后端：Next.js Server Actions / Route Handlers
- 数据库：PostgreSQL
- ORM：Prisma
- UI：
  - PC 端偏管理后台风格
  - 手机端做独立的轻量操作页面
- 身份认证：账号密码登录 + 角色权限
- 部署：阿里云 Linux 服务器 + Docker

### 5.2 为什么这样选

- 单人开发效率最高
- 代码统一，维护成本低
- 适合先做 PC 与移动网页双端
- PostgreSQL 适合交易、库存、报表类系统
- 未来接小程序、支付、消息能力时可继续复用后端

## 6. 支付与硬件策略

### 6.1 首发支付策略

- 第一阶段：
  - 微信记账
  - 支付宝记账
  - 现金
  - 银行卡
  - 储值余额
  - 次卡/赠送次数
- 第二阶段：
  - 接微信支付付款码支付 / Native / 小程序支付
  - 接支付宝当面付或相关线下支付能力

### 6.2 硬件策略

- 扫码枪：
  - 优先支持“键盘输入型扫码枪”
  - 浏览器可直接接收扫码内容
- 小票打印：
  - 第一版优先兼容浏览器打印和常见热敏打印流程
  - 后续再做指定品牌或 ESC/POS 深度适配
- 二维码核销：
  - 系统生成活动码
  - 现场扫码核销

## 7. 90 天排期

### 第 1 阶段：第 1-10 天

- 冻结核心需求
- 产出 PRD、流程图、权限图、数据模型草图
- 确定字段字典、角色、项目、提成、充值规则

### 第 2 阶段：第 11-20 天

- 搭建项目脚手架
- 搭建登录、权限、多店基础框架
- 建数据库和基础管理后台壳子

### 第 3 阶段：第 21-35 天

- 完成会员、家庭档案、充值方案、项目商品管理
- 完成门店、员工、角色基础管理

### 第 4 阶段：第 36-50 天

- 完成收银开单主流程
- 支持多项目、多员工、余额/次卡/赠送次数结算
- 支持基础订单查询

### 第 5 阶段：第 51-62 天

- 完成员工提成、库存扣减、退款撤单、充值退款、反结算
- 完成小票打印第一版

### 第 6 阶段：第 63-72 天

- 完成活动、优惠券、二维码核销
- 完成回访记录、自动提醒任务
- 完成基础报表

### 第 7 阶段：第 73-82 天

- 完成手机端高频页面
- 收银员、员工视角适配
- 优化流程和性能

### 第 8 阶段：第 83-90 天

- 门店实测
- 修复问题
- 部署上线
- 数据初始化
- 培训使用

## 8. 当前最大风险

1. 范围继续膨胀
2. 业务规则中途频繁变更
3. 支付资质和审核进度不可控
4. 小票打印机机型不统一
5. 退款、库存、提成之间的账务一致性处理复杂
6. 门店真实试用反馈可能推翻部分设计

## 9. 项目管理规则

1. 任何新增需求先进入需求池，不直接插队开发
2. 每周只做一次需求校对和流程测试
3. 所有提成、价格、充值规则都必须表格化确认
4. 所有核心流程先过“纸面流程”，再编码
5. 支付接入单独跟进，不阻塞主系统落地

## 10. 接下来 7 天该做什么

1. 把业务规则表彻底补齐
2. 输出第一版完整 PRD
3. 画系统流程图和权限图
4. 确认首批打印机和扫码枪型号
5. 梳理首批测试数据
6. 启动项目代码脚手架
